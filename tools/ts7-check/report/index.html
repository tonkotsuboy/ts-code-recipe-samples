このレポートの作り方（チェック手順）と結論の読み方

背景：なぜ「一括コンパイル」では測れないか

  • 本リポジトリは章×レシピで散在する独立スニペット集で、レシピ単位でしか型が閉じない。
  • 意図的な型エラーが多数（「こう書くと怒られる」解説用）。エラーが出るのが正解のファイルがあるため「エラーゼロ＝OK」では判定不能。
  • 同一フォルダ内でスニペットが同じ変数名を再宣言するため、フォルダをまとめてコンパイルすると重複宣言の偽エラーが出る。

→ そこで 「1ファイルずつ独立検査」＋「TS7 と tsc(安定版) の判定を比較」 という方針を採用。 意図的エラーは両方で同じく失敗するので、判定が食い違った箇所（DIVERGED）だけが TS7 固有の問題になる。

手順

  1. TS7 を導入：tools/ts7-check/ に typescript@7.0.2（Go製ネイティブコンパイラ）を npm エイリアス ts7rc で隔離インストール。
  2. 比較用に安定版 tsc も導入：typescript@Version 6.0.3。同じ入力を両方に通して差分を取るため。
  3. 全 .ts/.tsx を個別に型チェック：各ファイルを引数で直接渡し、--ignoreConfig でリポジトリルートの tsconfig.json を無視させる（付けないと TS6/TS7 とも TS5112 で即エラーになる）。これで変数衝突も避けられる。 書籍の設定に合わせ --noEmit --strict --module nodenext --target esnext --skipLibCheck --ignoreConfig（.tsx は --jsx react-jsx 追加）を毎回明示。合否は終了コード（0=PASS / 2=FAIL）で判定。
  4. TS7 と tsc を同条件で実行し比較：diverged = (TS7 の合否 ≠ tsc の合否)。これがゼロなら「TS7 にしても現行 tsc と同じ挙動」。
  5. 出力の「文言」も比較：msgDrift = (合否は同じ && 出力テキストが異なる)。 TS7 は stableTypeOrdering（既定ON・無効化不可）でリテラルUnionの表示順をソートし、テンプレートリテラル型の非ASCIIをエスケープしなくなったため、 合否が変わらなくてもエラー文が変わる。誌面がコンパイラー出力を引用している箇所の洗い出しに使う。
  6. 独自 tsconfig を持つフォルダはプロジェクト単位でも検査：-p <folder> で両方。設定見本（ch14 など）を本来の意図で評価するため。
  7. HTML / JSON に出力：このページ（report/index.html）と生データ report/results.json。

結論

per-file 826 件＋project 50 件すべてで TS7（tsc Version 7.0.2）と tsc（Version 6.0.3）の判定が完全一致。 TS7 固有の挙動差（DIVERGED）は 0 件、 文言だけが変わるもの（msgDrift）は 6 件。

エラーになる 134 件は TS7・tsc の両方で同じくエラー＝ 意図的な型エラー、nodenext でのESM拡張子要求、未インストールの外部型（zod / react など）、存在しない兄弟 import といった 互換性とは無関係の要因。よって 本サンプルは TypeScript 7 でも現行と同じように動く。
